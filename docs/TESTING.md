# Testing and quality verification

**Project:** Blossom E-commerce  
**Verification date:** November 16, 2026

## Strategy and coverage boundary

The backend uses a layered automated-testing approach:

| Layer | Tools | Focus |
|---|---|---|
| Unit | JUnit + Mockito | `ProductService`, `AuthService`, `OrderService`: pricing, stock, validation, JWT-related service behavior |
| HTTP/controller | MockMvc | Request validation, response status, response DTO and error contract |
| Security | MockMvc + Spring Security test context | Public routes, ADMIN/CUSTOMER roles, anonymous requests, invalid/expired JWT |
| Database integration | Spring Boot + Testcontainers PostgreSQL 17 | Actual JPA queries, order persistence, inventory update and schema mappings |
| Coverage | JaCoCo | Line coverage threshold enforced in Maven `verify` |
| Frontend static checks | ESLint + Vite | Hook conventions and production bundle generation |

The tests distinguish **mocked service dependencies** from **actual PostgreSQL integration**. A mocked repository test is valuable for service decisions but does not prove that a SQL query runs successfully against PostgreSQL. Testcontainers provides that separate verification.

## Reproduce tests

Prerequisites: Java 17 and Docker Desktop/Engine running (for Testcontainers). From `backend/`:

```powershell
.\mvnw.cmd clean verify
```

On Unix-like systems:

```bash
./mvnw clean verify
```

Open `backend/target/site/jacoco/index.html` after the build. XML and CSV reports, if generated by the configured plugin, are in the same JaCoCo report directory. The `target/` directory is intentionally ignored by Git; reviewers generate these reports locally.

For a targeted test (PowerShell quoting prevents argument parsing problems):

```powershell
.\mvnw.cmd "-Dtest=ProductServiceTest" test
```

Frontend:

```powershell
cd frontend
npm ci
npm run lint
npm run build
```

The captured frontend lint and build passed. The optional frontend unit-test extra is not included and should not be represented as completed.

## Test suites covered

- `ProductServiceTest`: create, read, update, soft delete, dynamic filtering and invalid ranges.
- `AuthServiceTest`: register, normalize email, duplicate registration, valid/invalid login and JWT response generation.
- `OrderServiceTest`: creation, totals, inventory decreases, duplicate items, missing/inactive products, invalid price, stock conflicts and JWT-subject validation.
- `AuthControllerTest`: registration/login and HTTP error validation.
- `ProductControllerTest`: CRUD request/response semantics and missing/invalid bodies.
- `OrderControllerTest`: protected creation, history, empty/invalid orders and conflict response.
- `SecurityIntegrationTest`: public catalog, permission enforcement, rejected invalid/expired tokens, allowed admin writes.
- `GlobalExceptionHandlerTest`: known HTTP statuses, bad payloads, conflicts and suppression of internal details.
- `EcommerceApplicationTests`: Spring context and real PostgreSQL 17 integration using ephemeral Testcontainers.

## End-to-end functional evidence

A sample customer purchased **2 units** of **Teclado Mecánico RGB** at **189,900 COP** each. The browser showed an order totaling **379,800 COP**, and database captures confirmed:

- `orders`: one order for the sample customer, status `CREATED`, total `379800.00`.
- `order_items`: one line with quantity 2, unit price `189900.00`, subtotal `379800.00`.
- `products`: stock decreased from 15 to 13.

This is a recorded functional demonstration, not an automated concurrency stress test.

## Known test-environment behavior

- Testcontainers starts a temporary PostgreSQL 17 instance; no developer PostgreSQL password is needed for `mvn verify`.
- A Maven Surefire warning about forcibly stopping a forked JVM appeared after tests completed. Maven still reported `BUILD SUCCESS` and zero test failures. Its cause is not yet conclusively established; monitor lifecycle ordering of Spring, Hikari and Testcontainers if it persists.
- Hikari logged closed-connection validation warnings while the test JVM was stopping. These are shutdown-time observations, not evidence of failed test assertions.
- Some compiler output noted an unchecked generic operation in a Mockito-based test. It does not change test outcomes; a targeted generic matcher can clean up that warning.

## Reproducible final acceptance

1. Run frontend `npm run lint` and `npm run build` successfully.
2. Run backend `mvn clean verify`: all tests green and JaCoCo threshold passed.
3. Run `docker compose config --quiet`, then `docker compose up -d --build`; confirm three services running.
4. Open `/api/products`, Swagger UI and the React landing page.
5. Register a test customer, create a demo admin through the documented controlled local seed, add a product, complete checkout and confirm order history.
6. Ensure no `.env`, secrets or generated build artifacts are committed.
